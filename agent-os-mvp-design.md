Version: v0.2 draft

Owner: Retailpulses GK

---

## 1. Background

Retailpulses GK operates multiple ecommerce channels, including Mercari Shops, Rakuten, and Amazon JP. The long-term vision is to build an internal Agent OS that can automate a significant part of ecommerce operations by combining structured business rules, platform data, local LLM workers, and human approval workflows.

The MVP does **not** aim to automate everything. It focuses on one narrow but valuable operational flow:

```text
Mercari Shop4 listing data
  → promotion candidate generation
  → Agent decision
  → human approval
  → mock execution log
  → future real platform execution
```

The first MVP is intentionally conservative. It validates whether Agent OS can create a traceable decision loop before connecting to real platform APIs or real LLM execution.

---

## 2. MVP Goal

The goal of this MVP is to establish the minimum architecture for a traceable Agent-driven promotion workflow.

The MVP should prove that the system can:

1. Import or seed listing data.
2. Generate promotion candidates based on simple business rules.
3. Create mock Agent decisions.//what is mock decisions and why mock?
4. Record human approval.
5. Record execution logs.
6. Trace all objects back to a single `agent_run`.
7. Avoid calling any real Mercari / Rakuten / Amazon APIs at this stage.

The MVP is not yet about model quality or real automation. It is about validating the operating model:

```text
Observe → Decide → Review → Execute → Log → Review again
```

---

## 3. Non-goals

The current MVP explicitly does **not** include:

- Real Mercari, Rakuten, or Amazon API execution.
- Qwen / local LLM integration.//why not included? then how the agent OS suppose to work?
- Full UI.
- Complex permission system.
- Supabase Row Level Security.
- pgvector / semantic search.
- Full order management.
- Full Baserow / Airtable migration.
- Image storage migration.
- Production-grade CI/CD.
- Dev / staging / production Supabase separation.

These are intentionally excluded to keep the MVP focused and debuggable.

## 5. Data Strategy

Supabase Postgres is used as the Agent OS core database.

It should hold data required for:

- Agent decision making.
- Human approval.
- Execution tracking.
- Auditability.
- Future replay and debugging.

It should **not** become a dumping ground for all business data.

### 5.1 Data that belongs in Agent OS Core DB

| Data | Reason |
|---|---|
| Products | Product master data for decision context |
| Product variants | SKU-level decision target |
| Platform listings | Platform-specific listing state |
| Promotion candidates | Candidate actions generated by rules or Agents |
| Agent decisions | AI or rule-based recommendations |
| Human approvals | Human-in-the-loop control |
| Execution logs | Audit trail for action attempts |
| Agent runs | Batch-level traceability |

### 5.2 Data that should stay outside for now

| Data | Current recommendation |
|---|---|
| Product images | Keep in Cloudflare R2 |
| Raw CSV exports | Keep as files / R2 later |
| Full historical orders | Do not migrate yet |//this will be very important soon as we try to analyze margin and product trends
| Full customer support history | Do not migrate yet |
| Airtable dashboards | Keep temporarily |
| Baserow operational tables | Keep temporarily |

- `spu_code`
- `title`
- `category`
- `status`
- `created_at`
- `updated_at`

---

### 6.2 `product_variants`

Purpose: SKU-level product variant data.

Key fields:

- `id`
- `product_id`
- `sku`
- `variant_name`
- `color`
- `size_text`
- `status`
- `created_at`

---

### 6.3 `platform_listings`

Purpose: Platform-specific listing state.

Key fields:

- `id`
- `variant_id`
- `platform`
- `shop_code`
- `external_listing_id`
- `title`
- `url`
- `current_price`
- `stock_qty`
- `listing_status`
- `raw_payload`
- `created_at`
- `updated_at`

Important constraint:

```text
unique(platform, shop_code, external_listing_id)
```

This allows the same SKU to exist across different shops or platforms.

---

- `listing_id`
- `candidate_type`
- `reason`

- `suggested_price`
- `status`
- `created_at`

Current status examples:

```text

approved
executed
skipped
failed
```

---

### 6.5 `agent_decisions`

- `model_name`

### 6.6 `human_approvals`

Purpose: Record human review and approval actions.

- `id`
- `run_id`
- `candidate_id`
- `reviewer`

- `comment`

---

### 6.7 `agent_execution_logs`

Purpose: Record execution attempts and results.

Key fields:

- `id`

- `candidate_id`
- `action_type`
- `target_platform`
- `target_shop_code`
- `status`
- `request_payload`
- `response_payload`
- `error_message`
- `created_at`

Current MVP uses mock execution only.

---

### 6.8 `agent_runs`

Purpose: Track each end-to-end task run.

- `id`

Example statuses:

```text

```

This table is the audit backbone of Agent OS.


The repo is designed to support both:

1. Direct CLI job execution.
2. Orchestrated flow execution.

Job files should avoid import side effects by using guarded `main()` execution.

Recommended pattern:

```ts
export async function runSomeStep() {
  // step logic
}

async function main() {
  await runSomeStep();
}

if (process.argv[1] === import.meta.filename) {
  main();
}
```

## 8. Current MVP Flow

### 8.1 Mock flow v2

Command:

```bash
npm run flow:mock:v2
```

Current flow:

```text
1. Create agent_run
2. Generate promotion candidates
3. Generate mock Agent decisions
4. Approve first pending candidate
5. Execute approved candidate with mock execution
6. Mark agent_run completed
```

Expected output summary:

```json
{
  "run_id": "...",
  "final_status": "completed",
  "candidates_created": 1,
  "candidates_skipped": 0,
  "decisions_created": 1,
  "decisions_skipped": 0,
  "approval_created": true,
  "execution_logs_created": 1,
  "execution_logs_skipped": 0
}
```

### 8.2 Candidate generation rule

Current simple rule:

```text
platform = mercari
shop_code = shop4
listing_status = active
stock_qty > 0
current_price is not null
```

Generated candidate:

```text
candidate_type = timesale_test
suggested_discount_rate = 5
suggested_price = current_price * 0.95
status = pending
```

## 10. Next Step: Listing Import MVP

The next milestone is to import external listing data without connecting to real platform APIs.

### 10.1 Purpose

Enable this path:

```text
Shop4 JSON / CSV export
  → import into Supabase
  → normalize product / variant / listing
  → run mock promotion flow
```

### 10.2 Recommended next files

```text
data/sample-shop4-listings.json
src/jobs/import-listings-from-json.ts
```

Later:

```text
data/sample-shop4-listings.csv
src/jobs/import-listings-from-csv.ts
```

### 10.3 Import behavior

For each listing record:

1. Upsert `products` by `spu_code`.
2. Upsert `product_variants` by `sku`.
3. Upsert `platform_listings` by:

```text
platform + shop_code + external_listing_id
```

The import job should report:

```text
products_created / products_updated
variants_created / variants_updated
listings_created / listings_updated
errors
```

### 10.4 Why JSON import before real API

Real platform API integration introduces uncertainty:

- API authentication.
- Rate limits.
- Platform data quirks.
- Network failures.
- Permission issues.

JSON import isolates data normalization first. This keeps debugging easier.

## 12. Key Design Principles

### 12.1 Traceability first

Every meaningful Agent OS action should answer:

```text
Which run created it?
What data was used?
What did the Agent decide?
Who approved it?
What was executed?
What was the result?
```

### 12.2 Human-in-the-loop by default

The MVP should not directly automate platform actions.

Default flow:

```text
Agent recommends
Human approves
System executes
```

### 12.3 Keep scripts composable

Each job should be usable in two ways:

1. Direct CLI execution.
2. Called by orchestrator.

Avoid import side effects.

### 12.4 Avoid premature platform coupling

Use JSON / CSV import before real platform API integration.

### 12.5 Avoid premature model coupling

Use mock Agent decisions before Qwen integration.

### 12.6 Avoid database dumping

Supabase should hold Agent OS core operational data, not every piece of historical business data.

## 13. Risks and Mitigations

| Risk | Description | Mitigation |
|---|---|---|
| Schema changes too early | Product/listing model may change | Keep schema simple and migration-based |
| Data source confusion | Baserow, Airtable, CSV, API may conflict | Define source priority later |
| Agent output quality unknown | Local model may produce inconsistent suggestions | Start with mock, then controlled Qwen worker |
| Accidental real execution | Agent might trigger platform action too early | No real adapter until approval model is stable |
| Audit gaps | Hard to debug why action happened | Use `agent_runs` and snapshots |
| Overbuilding UI | UI may slow down core validation | Use scripts and Supabase Studio first |
| Cost creep | Too many Supabase projects or compute upgrades | Use one project and local dev first |

1. JSON listing import works.//why JSON listings. I only have listing files in CSV file

3. Candidate generation works only on valid active listings with stock and price.
